# CodeDoctor 多智能体改造规划

> 状态：规划稿（尚未实施）  
> 目标：把单节点 `diagnose` 拆成 **分诊 → 修复 → 审查** 三个角色，验证环节保持为确定性代码  
> 前置阅读：`README.md` 的「诊断-修复-验证闭环」、`backend/graph.py`

---

## 1. 为什么要拆

### 1.1 当前架构的真实边界

`graph.py` 现在只有两个节点：

```
START → diagnose(检索 + LLM 结构化诊断) → verify(subprocess 真跑) → END / retry
```

这套设计的核心价值是 `verify`：**AI 说"修好了"不算数，代码真跑通过才算数**。但它有一个结构性盲区——

**真跑只能判断"能不能跑"，判断不了"改得对不对"。**

以下四种情况，`verify` 全部会误判为通过：

| 情况    | 例子                                      | verify 的结果    |
| ----- | --------------------------------------- | ------------- |
| 治标    | 把报错那行直接删掉 / 包一层 `try: ... except: pass` | ✔ 通过          |
| 偏离意图  | 求平均的报错 → 改成 `return 0`                  | ✔ 通过          |
| 引入新风险 | 修了除零，但引入了 `None` 传播                     | ✔ 通过（当前用例不触发） |
| 不完整   | 只给片段、缺 import，恰好没被执行到                   | ✔ 通过          |

同时，单个 `diagnose` 节点还要同时承担三件事：判断错误性质、决定修复策略、写出修复代码。**一件事做三件事，prompt 必然互相妥协。**

### 1.2 拆分的逻辑依据

| 能力            | 该由谁负责       | 理由                    |
| ------------- | ----------- | --------------------- |
| 判断"是什么病、该怎么治" | LLM + L1 正则 | 需要语义理解，但 18 类错误已有精确匹配 |
| 写出修复代码        | LLM         | 生成任务，需要专注             |
| 判断"是不是假修复"    | LLM（静态审查）   | 需要语义判断，真跑抓不到          |
| 判断"到底修好没有"    | **代码**      | 确定性，不可替代（红线）          |

前三个是判断/生成任务，可以交给 LLM；第四个是事实判定，必须留在代码里。

### 1.3 为什么是三个，不是五个

- **「专家 Agent」不独立存在**：它的本质是"用不同知识视角修"，通过分诊结果动态拼装 system prompt 即可实现，省一次调用、少一次信息传递。
- **「讲解 Agent」不独立存在**：`explain` / `reason` 在修复时一起产出更自然；单独拆出来只会把同一段话再说一遍。
- **每多一个角色，就多一次序列化和一次信息损耗**。本项目的 State 是结构化字段，损耗可控，但成本（token、延迟、调试难度）是线性叠加的。

**结论：3 个 LLM 角色 + 2 个代码环节（L1 检索、真实执行）。**

## 2. 三个 Agent 的分工

### 总览

|          | ① 分诊 Triage                                                   | ② 修复 Fixer                      | ③ 审查 Critic                         |
| -------- | ------------------------------------------------------------- | ------------------------------- | ----------------------------------- |
| **一句话**  | 判断是什么病、该怎么治                                                   | 开药方                             | 抓假药                                 |
| **运行时机** | 每轮开始                                                          | 每轮                              | 每次修复产出后、真跑之前                        |
| **输入**   | 原始代码、真实报错、L1 命中条目                                             | 代码、报错、分诊结果、知识条目、历史失败记录、审查意见（若有） | 原始代码、真实报错、修复全文、知识条目、Fixer 的风险自述     |
| **输出**   | `error_category` / `repair_strategy` / `focus` / `confidence` | `Diagnosis`（含 `risk_notes`）     | `verdict` / `issues[]` / `blocking` |
| **失败时**  | 降级为 `unknown` + `minimal_fix`                                 | 降级为知识库规则诊断                      | **fail-open（默认放行）**                 |

### 2.1 分诊 Triage

**职责**：在动手改之前，先把"这是什么类型的错、该用哪种修法"定下来。

**为什么必须独立**：语法错、逻辑错、环境依赖错的修法完全不同。

- `SyntaxError: expected ':'` → 改一个字符，`minimal_fix`
- `ModuleNotFoundError: No module named 'scipy'` → 不该改代码，该给安装指引，`env_guide`
- `ZeroDivisionError` + 逻辑本身有问题 → 可能需要重写算法，`logic_rewrite`

如果这三类混在一个 prompt 里让模型自己判断，它会在"改一行"和"重写"之间摇摆，产出不稳定的修复。

**输出结构**

```python
class Triage(BaseModel):
    error_category: Literal["syntax", "logic", "environment", "data", "unknown"]
    repair_strategy: Literal["minimal_fix", "logic_rewrite", "env_guide"]
    focus: str        # 重点关注的行/变量，一句话，如「第 4 行的 count」
    confidence: float # 0-1
    source: str       # "l1" | "llm"，由代码填写，不来自模型
```

**关键设计：L1 优先，LLM 兜底**

项目已有 `kb._l1_search(etype, message)`：错误类型必须一致，同类型内按 `message_patterns` 正则细分场景，命中具体条目优先，否则用该类型的兜底条目。

分诊直接复用这条路径：

```python
def triage(state) -> dict:
    hits = kb._l1_search(error_type, message)   # 与 kb.search 共用同一套规则
    if hits:
        return L1_MAP[error_type] + {"source": "l1", "confidence": 0.8}  # 不调 LLM
    return llm_triage(state)   # 仅未命中时调模型
```

`L1_MAP` 是一张静态映射表（18 类错误，来自 `knowledge/errors.json` 的 `error_type` 字段）：

| error_type                                                                                                                                       | category      | strategy        |
| ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------- | --------------- |
| `SyntaxError` / `IndentationError` / `TabError`                                                                                                  | `syntax`      | `minimal_fix`   |
| `NameError` / `UnboundLocalError` / `TypeError` / `ValueError` / `IndexError` / `KeyError` / `AttributeError` / `ZeroDivisionError` / `EOFError` | `logic`       | `minimal_fix`   |
| `ModuleNotFoundError` / `ImportError`                                                                                                            | `environment` | `env_guide`     |
| `FileNotFoundError` / `UnicodeDecodeError`                                                                                                       | `environment` | `minimal_fix`   |
| `RecursionError` / `__timeout__`                                                                                                                 | `logic`       | `logic_rewrite` |

注意两点：

1. **这张表给的是"倾向"，不是"硬约束"**。`confidence=0.8` 的含义是"类型确定，但策略可能需调整"，Fixer 的 prompt 里写成建议语气。
2. **L1 命中即跳过 LLM 分诊**，常见错误零额外调用、零额外延迟，且比模型更准（正则来自真实语料）。

### 2.2 修复 Fixer

**职责**：产出可运行的完整修复代码，并主动交代自己的改动范围。

**就是现在的 `llm.diagnose_stream()`，改两处：**

1. system prompt 按 `repair_strategy` 动态拼装：

| strategy        | prompt 侧重                                             |
| --------------- | ----------------------------------------------------- |
| `minimal_fix`   | 只改必要位置，最大程度保留原代码；不改结构、不改命名                            |
| `logic_rewrite` | 允许重写相关函数体，但必须保留输入输出语义和原有变量名                           |
| `env_guide`     | 优先给安装/环境指引；若用户环境无法改变，才给等价的标准库替代方案，并明确说明"这是替代方案，不是原方案" |

1. `Diagnosis` 增加一个字段 `risk_notes`：

```python
class Diagnosis(BaseModel):
    explain: str
    reason: str
    fix_points: list[str]
    error_line: int | None = None
    fixed_code: str
    risk_notes: str = Field(default="", description="你改动的影响范围与潜在副作用；没有就写「无」")
```

`risk_notes` 是**写给审查员的自首材料**：说明改了哪些行、可能影响什么。审查员据此重点核查。它是纯内部字段，前端不展示（想展示也很容易）。

> **实施注意**：新增字段不影响流式解析。`StreamFieldExtractor.__init__(fields=("explain", "reason", "fix_points", "fixed_code"))` 有一份字段白名单，不在名单里的字段直接被忽略——`risk_notes` 只需在最终结果里读取，不做流式抽取，无需改动 `stream_json.py`。

**输入要包含历史失败记录**：现有的 `llm.build_user_prompt(..., attempts=...)` 已经实现，重试时会把"上一版代码 + 它跑出的真实报错"一起喂回去。这条能力保持不动。

### 2.3 审查 Critic

**职责**：在真跑之前，用静态审查抓出 `verify` 抓不到的假修复。

**审四件事**（每一项都对应第 1.1 节的盲区）：

| # | 检查项      | 判定依据                                                 | 典型拦截         |
| - | -------- | ---------------------------------------------------- | ------------ |
| 1 | **治标**   | 是否删除报错行、是否用裸 `except: pass` 吞异常、是否直接 `return` 一个假值绕过 | 报错消失但问题还在    |
| 2 | **偏离意图** | 算法/语义是否被替换（对照原始代码与知识条目的 `fix_points`）                | 求平均变成返回 0    |
| 3 | **新风险**  | 是否引入新的未定义变量、类型不一致、`None` 传播、边界未处理                    | 修了除零，引入空列表崩溃 |
| 4 | **不完整**  | 是否缺少 import、是否只给片段、是否依赖未安装的库                         | 复制过去仍然报错     |

**输出结构**

```python
class Review(BaseModel):
    verdict: Literal["pass", "revise", "reject"]
    issues: list[str]   # 每条格式：「问题 + 证据（具体行）+ 建议」
    blocking: bool      # verdict == "pass" 时必须为 False
```

- `pass` → 进入 `verify`
- `revise` → 带审查意见回 `Fixer` 重写（**计入轮次**）
- `reject` → 极少用。保留给"用户的原始需求本身无法通过改代码满足"的情况，直接交付解释

**输入必须包含**：原始代码、真实报错、修复代码全文、命中的知识条目 `fix_points`、Fixer 的 `risk_notes`。

代码通常只有几十行，传全文比算 diff 更简单、更不容易出错。

**关键设计：fail-open**

审查这一步是**增强**，不是**闸门**。发生以下情况时一律放行，继续走 `verify`：

- LLM 调用失败 / 超时
- 返回的 JSON 无法解析
- `verdict` 字段非法

理由：`verify` 是确定性兜底，审查挂了不应该阻断主链路。**宁可漏审，不可误杀。**

> 与"验证永远是代码"这条红线的关系：审查员只做"建议打回"，**没有任何权限宣布代码没问题**。最终是否通过，永远由 `verify` 真跑决定。

## 3. 架构与数据流

```
                                ┌─────────────────────────────┐
                                │  State（共享，进程内）        │
                                │  code / error / stderr      │
                                │  triage / diagnosis         │
                                │  review / attempts / round  │
                                └─────────────────────────────┘
                                   ▲      ▲      ▲      ▲
                            读/写   │      │      │      │  读/写
        START                       │      │      │      │
          │                         │      │      │      │
          ▼                         │      │      │      │
   ┌─────────────┐                  │      │      │      │
   │ ① Triage    │──────────────────┘      │      │      │
   │ L1 命中→跳过 │                         │      │      │
   │ 否则调 LLM  │                         │      │      │
   └─────────────┘                         │      │      │
          │ triage 结果                     │      │      │
          ▼                                 │      │      │
   ┌─────────────┐                          │      │      │
   │ ② Fixer     │──────────────────────────┘      │      │
   │ 结构化输出   │                                 │      │
   │ +risk_notes │                                 │      │
   └─────────────┘                                 │      │
          │ diagnosis                              │      │
          ▼                                        │      │
   ┌─────────────┐                                 │      │
   │ ③ Critic    │─────────────────────────────────┘      │
   │ 静态审查     │                                        │
   └─────────────┘                                        │
      │        │                                           │
  revise│       │pass                                       │
      │        ▼                                           │
      │  ╔═══════════════╗                                 │
      │  ║  verify       ║◄────────────────────────────────┘
      │  ║  subprocess   ║         （代码环节，非 Agent）
      │  ║  真跑 + traceback 解析                        │
      │  ╚═══════════════╝
      │        │
      │   ┌────┴────┐
      │   │         │
      │  ok       fail
      │   │         │
      │   ▼         ▼
      │  END   回 Fixer（带新报错，round+1）
      │
      └──► 回 Fixer（带审查意见，round+1）

  轮次上限：round < CD_MAX_FIX_ROUNDS（默认 3）
  用尽仍未通过 → 如实交付「未通过验证」+ attempts 全轨迹
```

**注意两处细节**：

1. **critic 的回退与 verify 的回退都指向 Fixer，但携带的证据不同**：前者是审查意见，后者是真实新报错。State 里用不同字段承载（`review.issues` vs `stderr`/`error`），Fixer 的 prompt 分别处理。
2. **两条回退路径共用同一份轮次预算**。`round` 的语义统一为"第几次交付修复版本"，审查打回也算一次。

## 4. State 设计

在现有 `DoctorState` 基础上扩展（保持向后兼容：全部 `total=False`）：

```python
class DoctorState(TypedDict, total=False):
    # ---- 输入（不变）----
    code: str
    stdout: str
    stderr: str            # 当前最新一次运行的真实报错
    error: dict | None
    timed_out: bool

    # ---- 新增：分诊 ----
    triage: dict           # Triage.model_dump() + source

    # ---- 修复（原有）----
    diagnosis: dict        # Diagnosis.model_dump()，新增 risk_notes
    knowledge: list
    case_hits: list

    # ---- 新增：审查 ----
    review: dict           # Review.model_dump()
    review_rounds: int     # 本次诊断累计审查次数（用于观测，不参与路由）

    # ---- 验证（原有）----
    verify: dict | None
    verified: bool
    round: int             # 第几次交付修复版本
    max_rounds: int
    attempts: list         # 每轮记录，新增 gate 字段标明挂在哪一环
```

**`attempts` 的结构调整**（重要，否则前端轨迹会误报）：

```python
{
    "round": 1,
    "gate": "critic",          # "critic" | "verify"  ← 新增
    "ok": False,
    "fixed_code": "...",
    "error_summary": "审查打回:第 6 行用 bare except 吞掉了报错",  # critic 挂时填审查意见
    "stderr": "",              # verify 挂时填真实 stderr
}
```

现状是 `attempts` 只有 `error_summary`，如果审查打回也写"运行报错"，用户会看到"第 1 轮修复仍然报错"但实际根本没跑——**必须区分**。

**上下文控制**：`attempts` 中每轮只保留 `fixed_code`（约 1-3KB）+ `stderr` 最后 1200 字符（沿用现有逻辑），3 轮上限时 prompt 增量约 10KB，对 128K 上下文的 DeepSeek 完全无压力；对本地 7B（通常 8K-32K）需要留意，见第 9 节。

## 5. 节点实现要点

### 5.1 图谱接线

```python
def build_graph():
    g = StateGraph(DoctorState)
    g.add_node("triage", _triage_node)      # 新增
    g.add_node("fix", _fix_node)            # 原 diagnose_node 改名
    g.add_node("critic", _critic_node)      # 新增
    g.add_node("verify", _verify_node)      # 不变

    g.add_edge(START, "triage")
    g.add_edge("triage", "fix")
    g.add_edge("fix", "critic")
    g.add_conditional_edges("critic", _route_after_critic,
                            {"revise": "fix", "verify": "verify", "done": END})
    g.add_conditional_edges("verify", _route_after_verify,
                            {"retry": "fix", "done": END})
    return g.compile()
```


### 5.2 路由函数

```python
def _route_after_critic(state) -> str:
    review = state.get("review") or {}
    if review.get("verdict") == "revise" and _has_budget(state):
        return "revise"
    if review.get("verdict") == "reject":
        return "done"
    return "verify"

def _route_after_verify(state) -> str:
    if state.get("verified"):
        return "done"
    if not ((state.get("diagnosis") or {}).get("fixed_code") or "").strip():
        return "done"          # 规则模式没有可验证代码
    return "retry" if _has_budget(state) else "done"

def _has_budget(state) -> bool:
    return int(state.get("round", 0)) < int(state.get("max_rounds", config.MAX_FIX_ROUNDS))
```

### 5.3 事件推送（流式）

沿用现有 `_emit()` + contextvar 机制，新增三个 stage：

| stage           | 时机   | 前端文案                         |
| --------------- | ---- | ---------------------------- |
| `triage`        | 分诊开始 | 「正在判断错误类型…」（L1 命中时仅闪现）       |
| `review`        | 审查开始 | 「正在审查这个修复是否治标…」              |
| `review_result` | 审查结束 | 「审查通过，准备真实运行」/「审查不通过：{首条问题}」 |

前端改动极小：`applyStreamEvent` 里这三个 stage 走现有的 `status` 分支即可，无需新 UI 组件。

### 5.4 降级链总表

| 环节     | 主路径                 | 一级降级                       | 终极兜底                      |
| ------ | ------------------- | -------------------------- | ------------------------- |
| Triage | L1 正则命中             | LLM 分诊                     | `unknown` + `minimal_fix` |
| Fixer  | 结构化输出（LangChain）    | JSON 模式（`_json_mode_call`） | `kb.rule_diagnosis()`     |
| Critic | 结构化输出               | 解析失败即放行                    | 放行                        |
| Verify | `runner.run_python` | —                          | 视为未通过，如实标注                |

**每一层降级都不能让整条链路失败**——这是现有架构的既定原则，拆分后必须保持。

## 6. 通信机制：为什么不用协议

三个 Agent 在同一进程、同一张图里，**不引入任何通信协议**。

### 6.1 实际发生的事

```python
# 1. 上游节点把结果写回 State
def _triage_node(state):
    return {"triage": triage_result}      # 返回值合并进 State

# 2. 路由函数读 State 决定下一步
def _route_after_critic(state):
    return "verify" if state["review"]["verdict"] == "pass" else "revise"

# 3. 下游节点从 State 取输入
def _fix_node(state):
    strategy = state["triage"]["repair_strategy"]
```

这是分布式系统里的**黑板模式（blackboard）**：一块共享内存，谁需要谁读，谁产出谁写。开销为零——没有序列化、没有网络、没有握手。

注意 LangGraph 默认是**后写覆盖**（last-write-wins），项目目前没有使用 `Annotated[..., reducer]` 自定义合并。`attempts` 看着是追加，实际是节点内 `list(...)` 复制后 append 再整体覆盖。新增 `triage` / `review` 同样是覆盖语义，正好符合需要。

### 6.2 什么情况下才需要协议

| 触发条件                | 该用什么                            |
| ------------------- | ------------------------------- |
| 某个 Agent 需要独立部署/扩容  | HTTP + JSON（FastAPI 现成）         |
| 需要向浏览器流式回传          | SSE（`/api/diagnose/stream` 已在用） |
| 长任务异步解耦             | Redis Stream / RabbitMQ         |
| 把诊断能力开放给外部 Agent 调用 | A2A                             |

**A2A 才是"Agent 间通信协议"**：由 Google 发起、2026 年 4 月满一年时发布 v1.0 稳定版，现由 Linux Foundation 下的 Agentic AI Foundation（AAIF）治理。它定义 Agent Card 发现（`/.well-known/agent-card.json`）、Task/Message 语义、以及"不透明执行"（只交换能力与结果，不暴露内部记忆和工具）。

它解决的是**跨组织、跨厂商**的互操作问题。三个 Agent 都在同一个仓库、同一台机器上时，引入 A2A 只会带来额外负担：每个角色都要包成 HTTP 服务、维护 Agent Card、处理网络失败和版本协商，换来的"解耦"在这个规模下没有价值。

### 6.3 顺带澄清一个常见误解

**MCP 不是 Agent 间通信协议。** 它是纵向的——让单个 Agent 连接工具和数据源；A2A 是横向的——让 Agent 与 Agent 协作。两者在 Linux Foundation 下由同一个基金会治理，定位互补而非竞争。

本项目若要接 MCP，正确的方向是**对外暴露能力**（如 `diagnose_code` 工具给 Cursor 调用），而不是内部 Agent 之间用它通信。

## 7. 成本模型

以当前 DeepSeek 配置估算（首 token 约 1-2s，完整诊断 4-6s）：

| 场景             | Triage | Fixer | Critic | LLM 总调用 | 预计耗时   |
| -------------- | ------ | ----- | ------ | ------- | ------ |
| 简单错误，L1 命中，一次过 | 0      | 1     | 1      | **2**   | 8-11s  |
| L1 未命中         | 1      | 1     | 1      | **3**   | 12-16s |
| 审查打回一次         | 0-1    | 2     | 2      | **4**   | 18-24s |
| 最坏（3 轮全用尽）     | 1      | 3     | 3      | **7**   | 30-40s |

对比现状（1 次调用 / 4-6s）：**典型场景耗时约翻倍，调用次数翻倍**。

这是明确的取舍：用延迟和 token 换"假修复拦截率"。是否值得，必须靠第 10 节的对比测试来回答，而不是靠感觉。

**成本控制手段**：

- L1 命中跳过分诊（覆盖 18 类常见错误，占实际报错的多数）
- `max_rounds` 复用现有 `CD_MAX_FIX_ROUNDS`（默认 3），不新增轮次预算
- Critic 只审一次，`revise` 后不再复审（避免"审查-打回"死循环），直接进 `verify`

> 最后一条是有意的简化：`revise` 后的版本不再过 Critic，直接真跑。理由是打回一次已经足够暴露主要问题，而验证是更硬的裁判。如果对比测试显示二次审查收益明显，再放开这个限制。

## 9. 实施计划

### Step 1：拆节点（行为不变）

- `_diagnose_node` 拆成 `_triage_node` + `_fix_node`
- `_triage_node` 暂时只做 L1 查询并写 `state["triage"]`，不接 LLM
- `_fix_node` 复用现有逻辑，prompt 拼接 `triage` 结果
- **验收**：现有全部测试通过，输出与改造前逐字段一致（除新增 `triage` 字段）

这一步是纯重构，风险最低，且能立刻验证"拆分本身没有破坏任何东西"。

### Step 2：接 LLM 分诊

- 补 `llm.triage()`（结构化输出 + `L1_MAP` 兜底）
- **验收**：18 类错误的分类准确率测试（用 `errors.json` 的 `example_bad` 构造用例）

### Step 3：加 Critic

- 新增 `_critic_node` + `Review` 模型 + 条件边
- `attempts` 增加 `gate` 字段
- **验收**：构造 3 个"故意治标"的修复，全部被拦截；5 个正确修复，误杀 ≤ 1

### Step 4：前端 + 文档

- 三个新 stage 的状态行
- 轮次轨迹区分 gate
- README 更新"三个 Agent"章节

### 每步都要跑

## 10. 验收标准与对比测试

### 10.1 硬性验收

| 项      | 标准                                     |
| ------ | -------------------------------------- |
| 现有功能回归 | 上述 4 个测试脚本全部通过，零退化                     |
| 假修复拦截  | 3 个构造用例（删行 / 吞异常 / 换算法）全部被 Critic 拦下   |
| 误杀率    | 5 个真实正确修复中，被打回 ≤ 1 个                   |
| 降级可用   | 断网 / 无 Key / 模型返回非 JSON 三种情况下，仍能产出诊断结果 |

### 10.2 对比测试设计（这是最有价值的部分）

**同一批 10 个用例，跑两遍：旧单节点 vs 新三 Agent。**

用例设计（`tmp/mas_bench/`）：

| 类型                | 数量 | 目的             |
| ----------------- | -- | -------------- |
| 简单语法错（L1 命中）      | 3  | 验证基础能力不退化、成本可控 |
| 多错叠加（需多轮）         | 3  | 验证重试链路         |
| 诱导治标（如"报错了就删掉这行"） | 2  | 验证 Critic 价值   |
| 逻辑错误（算法本身有问题）     | 2  | 验证分诊策略是否影响修复质量 |

**记录指标**：

```
修复通过率        = verify 通过数 / 总数
假修复数          = 通过验证但人工判定为治标的数量
平均 LLM 调用次数
平均耗时
平均轮次
```

**只有"假修复数显著下降、且通过率不下降"才算成功。** 如果通过率掉了，说明 Critic 在误杀，需要调 prompt 或放宽判定。

### 10.3 一个必须提前说明的约束

**本地 `qwen2.5:7b` 不适合验证这套架构。**

多智能体的前提是"单个角色已经足够强"。7B 在每个角色上都会出错，串联后误差是**放大**而不是抵消的。在这种配置下做对比测试，很容易得出"加了 Agent 反而更差"的结论——但那是模型能力问题，不是架构问题。

**对比测试必须在 DeepSeek 上跑。** 本地模型的价值是"能不能跑通"，不是"好不好"。

## 11. 风险清单

| 风险            | 影响                  | 缓解                                                        |
| ------------- | ------------------- | --------------------------------------------------------- |
| Critic 误杀正确修复 | 用户拿到更差的诊断，甚至死循环     | fail-open 降级；`revise` 后不再复审；保留 `reject` 但极少用              |
| 延迟翻倍          | 简单错误从 5s 变 10s，体感变差 | L1 命中跳过分诊；流式展示三个阶段让等待"有内容"                                |
| 上下文膨胀         | 本地 7B 超窗口           | 每轮 `fixed_code` 截断、`stderr` 保留尾部 1200 字符；超限时丢弃最早的 attempt |
| 角色间信息损耗       | Fixer 拿不到审查的真实意图    | State 传结构化字段，不传自然语言摘要（这条是架构天然优势）                          |
| 成本失控          | token 消耗 3-5 倍      | 轮次上限不变（3）；L1 跳过；开发期用短用例压测                                 |
| 分诊分类错误        | 修法选错，导致更多轮次         | L1 映射表来自真实语料，比模型判断更准；`confidence` 低时让 Fixer 自行判断          |

---

## 12. 不做什么（明确边界）

- **不改验证环节**：`runner.run_python` + `traceback_parser` 保持原样，不接受 LLM 参与"是否修好了"的判定
- **不改通信层**：三个 Agent 走共享 State，不引入 HTTP/A2A/MQ
- **不拆讲解 Agent**：`explain` / `reason` 继续由 Fixer 一起产出
- **不改现有接口**：`/api/diagnose`、`/api/diagnose/stream`、`/api/chat/stream` 的请求/响应结构保持兼容（只新增字段）
- **不做动态 Agent 编排**：图结构固定，不引入"模型决定调哪个 Agent"的自主路由
