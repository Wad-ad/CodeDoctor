# CodeDoctor —— 简历项目简介

> 面向编程初学者的 AI 报错诊断助手。核心差异:**AI 会先把代码真实跑一遍,再开口诊断;给出的修复代码必须真跑通过才交付。**

---

## 一、一句话介绍(放个人总结 / 自我介绍)

**CodeDoctor** 是一个「会先复现、再确诊」的 AI 编程助教:它基于 LangGraph 编排分诊、修复、审查三个角色,所有修复代码都在服务端真实执行验证,跑不通就带着新报错自动重试;支持流式诊断、多轮追问与 RAG 案例库。

---

## 二、技术栈

| 层 | 技术 |
|---|---|
| 后端 | Python 3.13、FastAPI、Pydantic、SSE |
| AI 编排 | LangChain(结构化输出)、LangGraph(状态图 + 条件边 + 重试)、DeepSeek / 本地 Ollama 双后端 |
| 检索 | Chroma、bge-m3(硅基流动云端 / Ollama 本地可切换)、L1 精确索引 + L2 向量分层检索 |
| RAG | LangChain 文档加载器(md/txt/docx/pdf)、Markdown 标题切分 + 递归切分、代码块保护 |
| 前端 | Vue 3、Vite、Monaco Editor、流式渲染 |
| 执行引擎 | subprocess 隔离执行、超时终止、traceback 解析 |

**规模**:后端约 3.1k 行 Python,前端约 2.1k 行,8 个 REST / SSE 接口,22 个测试脚本。

## 三、简历精简版(推荐,直接粘 4 条)

- **主导设计与实现 AI 编程助教 CodeDoctor**(FastAPI + Vue3 + LangGraph,后端 3.1k 行 / 前端 2.1k 行,8 个接口),解决初学者「看不懂报错、不知道改哪」的问题。
- **设计「真实执行 + 诊断 + 验证」闭环**:基于 subprocess 构建隔离执行引擎(临时目录、10s 超时、强制 UTF-8),自研 traceback 解析器提取异常类型、报错行号与代码片段;修复代码必须真跑通过才交付,失败则带新报错重试(≤3 轮),避免模型「凭空猜测」。
- **实现三阶段多角色工作流**:Triage(复用 30 条 / 18 类 / 42 条正则的精确索引,命中时 0 次模型调用)→ Fixer(按错误类型注入修复策略)→ Critic(拦截删报错行、裸 except、偏离原意等假修复,自建用例拦截 3/3)→ Verify(确定性真跑);并搭建 L1 精确 + L2 向量(bge-m3 + Chroma)的分层知识库与 md/docx/pdf 案例库 RAG。
- **实现 SSE 流式诊断与多轮追问**:自研增量 JSON 状态机从 token 流实时抽取字段,首字 4.6s 出现(总耗时 7.7s);追问支持意图识别,「为什么不那样改」会按用户思路真实改码并执行验证,走不通则输出「原因 / 技术限制 / 潜在问题 / 建议」四段结构化解释;意图分类 12/12、多轮链路 E2E 12/12、Chrome 真机验证 17/17。

## 四、简历完整版(项目经历展开,可按篇幅删减)

- **项目定位**:面向编程初学者的 AI 报错诊断助手,覆盖「运行 → 定位 → 解释 → 修复 → 验证 → 追问」完整链路。
- **真实执行引擎**:使用 `subprocess` 在临时目录隔离执行用户代码,强制 UTF-8、关闭 stdin、10s 超时终止;自研 traceback 解析器,从原始 stderr 中提取异常类型、消息、报错行号与该行代码,为后续诊断提供可核验的事实依据。
- **LangGraph 诊断闭环**:将流程建模为状态图,`triage → fix → critic → verify` 条件边驱动;修复代码在服务端真实运行,未通过则携带「上一版代码 + 真实报错」回到修复节点重试,最多 3 轮;拿不到验证结果时如实标注,不假装成功。
- **三阶段多角色设计**:分诊只判断「是什么病、该怎么治」,修复专注「怎么改对」,审查在真跑前拦截治标式修复;三者使用独立 prompt、独立输入 schema、独立上下文(分诊看不到历史失败、审查看不到程序输出),通过结构化 State 传递结果,避免信息串联污染。
- **分层知识检索**:以 `errors.json`(30 条语料 / 18 类异常 / 42 条消息正则)为唯一知识源,L1 用「异常类型 + 消息正则」做精确匹配,命中即确定;未命中才走 L2(bge-m3 + Chroma,带距离阈值)。自建 18 条真实报错评测:向量模式 top-3 召回 17/18,但 top-1 仅 13/18,据此确定「L1 优先、向量兜长尾」的策略。
- **RAG 案例文档库**:支持 md / txt / docx / pdf 上传,使用 LangChain 加载器 + Markdown 标题切分 + 递归字符切分,并对代码块做「切分前占位保护」,避免把完整示例切碎;内容哈希保证重复上传幂等,嵌入后端指纹变化时自动从原文重建索引。
- **流式诊断体验**:基于 FastAPI StreamingResponse + 后台线程 + 队列实现 SSE;自研逐字符 JSON 状态机,从模型输出的 token 流中增量提取 explain / reason / fix_points / fixed_code,前端实现打字机效果、阶段状态、轮次轨迹与完成态卡片;含「流式结构化 → 流式纯文本 → 非流式」三级降级。
- **多轮追问与替代方案**:服务端会话保存代码、真实报错、诊断结果与完整对话;LLM 意图分类区分「问原理」与「提出替代方案」,后者会按用户思路生成代码并真实执行验证,成功则交付新方案并更新上下文,失败则输出结构化的不可行分析;程序跑通后追问区仍然保留。
- **工程质量**:22 个测试脚本覆盖解析器单测、HTTP 端到端、SSE 流式与 Chrome CDP 真机验证;关键指标——意图分类 12/12、多轮追问 E2E 12/12、真机交互 17/17、假修复拦截 3/3、审查误杀 1/5。

## 七、技术难点与取舍(面试问答准备)

**1. 为什么用固定工作流,而不是让模型自主决定调什么工具?**
诊断顺序是物理确定的:不跑代码就不知道真实报错,不验证就不能说修好了。让模型决定「要不要验证」等于把最确定的环节交给最不确定的东西。因此流程用 LangGraph 写死,模型只负责「内容」(解释、策略、修复代码),不负责「流程」。

**2. 为什么知识库先查 L1,不直接走向量?**
异常类型是解释器给出的硬标签,不是自然语言。实测同一批 18 条报错:向量 top-1 只有 13/18,且错配方向危险(IndexError→ValueError、KeyError→NameError、该缩进→多缩进);L1 用「类型 + 消息正则」可以精确到唯一场景,还省掉一次 embedding 调用。所以 L1 优先、向量兜长尾。

**3. 为什么验证必须由代码完成?**
一旦让模型判断「这个修复应该可以了」,项目就从「医生」退化成「算命」。`runner` 真跑 + traceback 解析是确定性的,这是产品立足点,不能被任何角色替代。

**4. 审查角色为什么是 fail-open?**
审查是增强项,不是硬门槛。模型超时、返回坏 JSON 时一律放行,交给真实验证裁决;宁可漏审,不可误杀。

**5. 多角色会不会导致上下文丢失?**
State 传结构化字段(原始代码、真实 stderr、每轮尝试记录),不传自然语言摘要;每个角色独立构造 messages、不给历史对话,避免措辞锚定。
