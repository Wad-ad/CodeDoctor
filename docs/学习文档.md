## 1. 全景:一次诊断到底发生了什么

### 1.1 一句话定位

**CodeDoctor 是一个"先复现、再确诊"的 AI 编程助教**:用户代码先在服务端真实运行,拿到真实报错后再让模型诊断;模型给出的修复代码还要再真实运行一遍,通过才交付。

`【核心】` 这个项目最值钱的东西不是"接了大模型",而是**两次真实执行**:一次复现问题,一次验证修复。模型只负责"内容",不负责"事实"。

### 1.2 分层架构

```text

│  · 代码编辑 / 报错行标红 / 修复一键填回 / 流式渲染              │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTP + SSE
┌───────────────▼──────────────────────────────────────────────┐
│  FastAPI (main.py)  8 个接口                                  │
│                                                              │
│  ┌─────────────┐   ┌──────────────┐   ┌───────────────────┐  │
│  │ runner.py   │   │ graph.py     │   │ chat.py           │  │

### 1.3 一次完整诊断的 8 个步骤

| 步骤 | 谁在做 | 输入 | 输出 |
|---|---|---|---|
| ① 运行 | 前端 → `/api/run` | 用户代码 | stdout / stderr / exit_code |
| ② 解析 | `traceback_parser` | stderr + 源码 | type / message / line / snippet |
| ③ 连流 | 前端 → `/api/diagnose/stream` | 代码 + 真实运行结果 | SSE 连接 |
| ④ 分诊 | `triage` 节点 | 报错类型 + 消息 | 错误类别 + 修复策略 |
| ⑤ 修复 | `fix` 节点 | 代码 + 报错 + 知识 + 案例 + 历史 | explain / reason / fix_points / fixed_code |
| ⑥ 审查 | `critic` 节点 | 原代码 + 报错 + 修复代码 | pass / revise + 问题清单 |
| ⑦ 验证 | `verify` 节点 | 修复代码 | 真跑结果(通过 / 新报错) |
| ⑧ 交付 | `_deliver()` | 图终态 | 带 `verified` 的完整诊断 |

没通过就回到 ⑤,带着"上一版代码 + 它跑出的真实报错"重试,最多 3 轮。

## 2. 执行引擎:整个项目的地基

### 2.1 为什么不用 `exec()`

| 方案 | 问题 |
|---|---|
| `exec(code)` | 跑在服务进程里:死循环直接卡死服务;异常会污染进程状态;无法设置超时;报错行号是 `<string>`,不好定位 |
| `eval()` | 只能算表达式,不能跑完整程序 |
| **`subprocess`** | 独立进程,可超时终止;崩溃不影响服务;traceback 与真实运行完全一致;行号可解析 |

`【核心】` 选择子进程不是"更安全",而是**可终止 + 报错真实**。安全是另一件事(见第 12 章)。

### 2.2 核心代码

`backend/runner.py:33-51`:

```python
def run_python(code: str) -> dict:
    with tempfile.TemporaryDirectory(prefix="codedoctor_") as tmp:
        script = Path(tmp) / "main.py"
        script.write_text(code, encoding="utf-8")

        env = os.environ.copy()
        env["PYTHONIOENCODING"] = "utf-8"
        env["PYTHONUNBUFFERED"] = "1"

        proc = subprocess.run(
            [sys.executable, "-X", "utf8", str(script)],   # 同一个解释器,独立进程
            capture_output=True,
            timeout=config.EXEC_TIMEOUT,                   # 默认 10 秒
            cwd=tmp,                                       # 工作目录隔离
            env=env,
            stdin=subprocess.DEVNULL,                      # input() 直接 EOF
        )
```

### 2.3 每个参数的作用

| 参数 | 作用 | 不做会怎样 |
|---|---|---|
| `TemporaryDirectory` | 每次请求独立目录,结束自动清理 | 用户文件互相污染,残留垃圾 |
| `-X utf8` + `PYTHONIOENCODING` | 强制 UTF-8 | Windows 下中文输出乱码 / `UnicodeEncodeError` |
| `timeout=10` | 超时终止 | `while True` 永久占住一个线程 |
| `cwd=tmp` | 相对路径落在临时目录 | `open("data.txt")` 读写到项目目录 |
| `stdin=DEVNULL` | 没有输入 | `input()` 挂起,直到超时 |
| `capture_output` | 拿到 stdout/stderr | 无法诊断 |
| 输出截断 20000 字符 | 防止撑爆响应 | 大输出打爆内存/网络 |

`【易错】` `cwd` 只隔离**相对路径**。用户写 `open(r"D:\00\CodeDoctor\backend\.env")` 依然能读到。这不是权限隔离。

### 2.4 超时处理

`backend/runner.py:56-64`:

```python
except subprocess.TimeoutExpired as exc:
    stdout = _decode(exc.stdout)
    stderr = _decode(exc.stderr)
    stderr += (
        f"\n[CodeDoctor] 程序运行超过 {config.EXEC_TIMEOUT} 秒仍没有结束,已被自动终止。\n"
        "最常见的原因:代码里有停不下来的死循环(比如 while True 没有退出条件)。"
    )
    exit_code = -1
    timed_out = True
```

`【易错】` `subprocess.run` 超时只杀**直接子进程**。如果用户代码自己 `Popen` 了后台进程,孙进程会活下来。要彻底解决需要 Job Object(Windows)或进程组(Linux)。

## 3. traceback 解析:从一坨红字里提取四个关键信息

### 3.1 目标

把这段文本:

```text
Traceback (most recent call last):
  File "C:\...\Temp\codedoctor_xxx\main.py", line 3, in <module>
    average = sum(scores) / count
ZeroDivisionError: division by zero
```

变成:

```python
{"type": "ZeroDivisionError", "message": "division by zero", "line": 3, "snippet": "average = sum(scores) / count"}
```

### 3.2 算法三步

`backend/traceback_parser.py:15-59`,核心逻辑:

```python
# 1) 从最后一行往上找「异常行」
for i in range(len(lines) - 1, -1, -1):
    line = lines[i]
    if not line or line[0] in " \t":
        continue
    m = _EXC_LINE_RE.match(line)
    if m and _looks_like_exception(m.group(1)):
        exc_type = m.group(1)
        exc_msg = (m.group(2) or "").strip()
        exc_index = i
        break

# 2) 从异常行往上找最后一个指向 main.py 的 File 行
for i in range(exc_index, -1, -1):
    m = _FILE_LINE_RE.search(lines[i])
    if m and m.group(1).replace("\\", "/").endswith("main.py"):
        line_no = int(m.group(2))
        break

# 3) 报错行的代码直接从用户代码里取
code_lines = code.splitlines()
if line_no and 1 <= line_no <= len(code_lines):
    snippet = code_lines[line_no - 1].strip()
```

### 3.3 三个值得学的细节

`【核心】` **用后缀判断"这是不是异常行"**,而不是匹配所有大写单词:

```python
_EXCEPTION_SUFFIXES = ("Error", "Exception", "Interrupt", "Exit", "Iteration", "Group")
```

Python 的异常类都以这些结尾,这样不会把普通输出("RESULT: 42")误判成异常。

`【核心】` **行号取"最后一个 `main.py`"**,而不是第一个。因为重试/嵌套时 traceback 里会出现多层 `File`,最后一个才指向用户代码真正出错的位置。

`【核心】` **snippet 从源码取,不从 traceback 抠**。traceback 里那行可能被截断、可能带 `^^^^` 标记;直接从 `code.splitlines()[line-1]` 取最可靠。

`【易错】` SyntaxError 的 traceback 行号有时指向解析失败的位置,片段可能为空;解析器用 `1 <= line <= len(code_lines)` 做了保护,越界就返回空串而不是崩溃。

## 4. 结构化输出:让模型"填表"而不是"写作文"

### 4.1 为什么需要

如果让模型自由输出,前端要解析"发生了什么 / 为什么 / 怎么改",只能靠正则猜,格式一变就崩。解决方案:**用 Pydantic 定义 schema,强制模型按字段填**。

`backend/llm.py:32-43`:

```python
class Diagnosis(BaseModel):
    explain: str = Field(description="用一两句大白话说明程序发生了什么")
    reason: str = Field(description="结合报错信息,解释为什么会出现这个问题")
    fix_points: list[str] = Field(default_factory=list, description="修改点列表")
    error_line: int | None = Field(default=None, description="报错所在行号")
    fixed_code: str = Field(description="修复后的完整代码;不要 markdown 围栏")
    risk_notes: str = Field(default="", description="改动范围与潜在副作用(写给审查员看)")
```

`【核心】` **schema 一处定义,全程使用**:模型输出、Pydantic 校验、前端渲染、验证节点取 `fixed_code`,用的都是同一个模型。这叫"字段即契约"。

### 4.2 三种实现方式

`backend/llm.py:353-358`:

```python
if config.is_ollama():
    structured = llm.with_structured_output(Diagnosis)          # Ollama 原生
else:
    structured = llm.with_structured_output(Diagnosis, method=config.STRUCTURED_METHOD)
```

| 后端 | 机制 | 说明 |
|---|---|---|
| Ollama | 原生 structured output | 底层走模型的 JSON 能力 / grammar |
| 云端(默认 `function_calling`) | 把 schema 转成"函数定义" | 模型"调用"一个虚构函数,参数就是字段 |
| `json_schema` / `json_mode` | 强制 JSON | 兼容性更好,但校验弱一些 |

`【面试】` 被问"你用 Agent 工具了吗",准确回答:**用了 tool calling 做结构化输出约束,但流程编排是固定状态图,不是模型自主调工具**。第 4.3 节就是这个区别的证据。

### 4.3 三级降级链

`backend/llm.py:353-365`:

```python
try:
    data = _to_dict(structured.invoke(msgs))       # ① 结构化输出
except Exception as primary_exc:
    try:
        data = _json_mode_call(msgs)               # ② 提示词约束 JSON + 手动解析
    except Exception as fallback_exc:
        raise RuntimeError(...)                    # ③ 交给调用方退回知识库规则
```

`【核心】` 降级不是"可选项",是**产品可用性的底线**:7B 本地模型、网络抖动、模型不支持的字段,任何一环失败都不能让整个诊断没有结果。

### 4.4 围栏清理

模型经常把代码包在 ` ```python ` 里。`_strip_code_fence`(`llm.py:228-233`)用两条正则去掉首尾围栏:

```python
text = re.sub(r"^```[A-Za-z0-9_+.\-]*\s*\n?", "", text)
text = re.sub(r"\n?```\s*$", "", text)
```

`【易错】` 只在**最终交付值**上清理,流式中间态仍可能带围栏。测试比对时要用同一口径规范化,否则会出现"流式拼接 153 字符 vs 最终 152 字符"的假失败。

## 5. LangGraph:把诊断流程写成一张图

### 5.1 为什么用图,不用 while 循环

| 写法 | 可观测性 | 可测试性 | 重试逻辑 | 可视化 |
|---|---|---|---|---|
| `while` + if | 靠打日志 | 要 mock 整个循环 | 散落在代码里 | 无 |
| **LangGraph** | 每个节点是纯函数 | 可以单独调用节点 | 条件边集中声明 | 自动出图 |

`【核心】` 图的价值不是"更高级",而是**把"下一步做什么"从代码里提出来,变成可检查的边**。

### 5.2 State:节点之间唯一的事实来源

`backend/graph.py:44-59`:

```python
class DoctorState(TypedDict, total=False):
    code: str
    stdout: str
    stderr: str            # 当前最新一次运行的真实报错(重试轮会更新)
    error: dict | None
    timed_out: bool
    round: int
    max_rounds: int
    triage: dict           # 分诊结论
    knowledge: list
    case_hits: list
    diagnosis: dict
    review: dict           # 审查结论
    verify: dict | None
    verified: bool
    attempts: list
```

节点是纯函数:**读 state,返回"要合并进去的字段"**:

```python
def _verify_node(state):
    ...
    return {"verify": result, "verified": ok, "attempts": attempts, "round": round_no}
```

`【核心】` LangGraph 默认是**后写覆盖**,不是追加。`attempts` 看起来在 append,实际是节点里 `list(...)` 复制一份、append 完整体返回,本质仍是覆盖写。想用 reducer 追加,需要 `Annotated[list, operator.add]`。

### 5.3 图接线

`backend/graph.py:362-376`:

```python
g = StateGraph(DoctorState)
g.add_node("triage", _triage_node)
g.add_node("fix", _fix_node)
g.add_node("critic", _critic_node)
g.add_node("verify", _verify_node)
g.add_edge(START, "triage")
g.add_edge("triage", "fix")
g.add_edge("fix", "critic")
g.add_conditional_edges(
    "critic", _route_after_critic,
    {"retry": "fix", "verify": "verify", "done": END},
)
g.add_conditional_edges("verify", _route_after_verify, {"retry": "fix", "done": END})
```

画成图:

```text
START → triage → fix → critic ─┬─ pass   → verify ─┬─ 通过 → END
                  ↑            ├─ revise → fix     └─ 没通过 → fix(有预算)
                  └────────────┘
```

### 5.4 两个路由函数

`backend/graph.py:342-359`:

```python
def _route_after_critic(state):
    verdict = (state.get("review") or {}).get("verdict") or "pass"
    if verdict == "reject":
        return "done"
    if verdict == "revise":
        return "retry" if _has_budget(state) else "done"
    return "verify"

def _route_after_verify(state):
    if state.get("verified"):
        return "done"
    fixed_code = ((state.get("diagnosis") or {}).get("fixed_code") or "").strip()
    if not fixed_code:
        return "done"          # 规则模式没有修复代码
    return "retry" if _has_budget(state) else "done"
```

`_has_budget` 的定义只有一行:**`round < max_rounds`**。`round` 的语义是"已产出的修复版本数",审查打回和验证失败都消耗它。

### 5.5 流式事件:contextvar 注入 sink

`backend/graph.py:31-41`:

```python
_EVENT_SINK = contextvars.ContextVar("codoctor_event_sink", default=None)

def _emit(event: dict):
    sink = _EVENT_SINK.get()
    if sink is not None:
        try:
            sink(event)
        except Exception:
            pass
```

`【核心】` 这是"**不改变同步调用也能支持流式**"的关键:节点里只写 `_emit(...)`,不关心有没有人听;`run_diagnosis()` 不注入 sink,`_emit` 就是 no-op;`run_diagnosis_stream()` 注入 `events.put`,事件就流到 SSE。

`【易错】` contextvar 必须**在同一个执行上下文里 set**。LangGraph 在线程池里跑节点,所以要在调用 `GRAPH.invoke` 的线程里 set,而不是在 FastAPI 主线程 set 完就完事。

### 5.6 recursion_limit 的计算

```python
config={"recursion_limit": config.MAX_FIX_ROUNDS * 3 + 8}
```

最坏路径:每轮经过 `fix → critic → verify` 三个节点,再加首尾。3 轮 × 3 + 8 = 17,留足余量。`【易错】` 设太小会抛 `GraphRecursionError`,表现为"诊断突然失败",而不是"轮数用完"。

## 6. 三阶段多角色:分诊、修复、审查

### 6.1 角色分工

| | 分诊 Triage | 修复 Fixer | 审查 Critic |
|---|---|---|---|
| 一句话 | 判断是什么病、怎么治 | 开药方 | 抓假药 |
| system prompt | `TRIAGE_PROMPT` | `SYSTEM_PROMPT` | `REVIEW_PROMPT` |
| 输出 schema | `Triage` | `Diagnosis` | `Review` |
| 输入 | 代码 + 报错 + stderr | 代码 + 报错 + stdout + 知识 + 案例 + 历史 + 策略 | 原代码 + 报错 + 修复代码 + 风险自述 |
| 看不到 | stdout / 历史 / 修复代码 | —— | stdout / 历史 / 案例 |
| 是否调模型 | L1 命中时不调 | 必调 | 必调(可 fail-open) |

`【核心】` 三者不是"同一个 prompt 跑三遍",而是**三套 prompt、三套 schema、三套输入**。上下文隔离的证据就是函数签名:

```python
def triage(code, error, stderr="", timed_out=False, knowledge="")        # 没有 attempts
def diagnose(code, error, stdout="", stderr="", ..., attempts=None, strategy="", focus="")
def review(code, error, fixed_code, knowledge="", risk_notes="")         # 没有 stdout
```

### 6.4 审查:抓真跑抓不到的假修复

`verify` 只能判断"能不能跑",判断不了"改得对不对"。审查专抓四类:

1. **治标**:删报错行、删整条语句、裸 `except` 吞异常、直接 `return` 假值
2. **偏离意图**:求平均变成返回 0、求和变成求个数
3. **新风险**:未定义变量、类型不一致、`None` 传播、死循环
4. **不完整**:缺 `import`、只给片段、依赖没装的库

`【核心】` 审查必须**看完整分支**。项目里踩过:修复代码是

```python
if b != 0:
    print(a / b)
else:
    print("除数不能为0")
```

审查员只看到 `if`,就判"输出被屏蔽";其实 `else` 分支有交代。这条教训直接写进了 `REVIEW_PROMPT`(`llm.py:127-128`)。

### 6.5 fail-open:宁可漏审,不可误杀

`backend/graph.py:244-247`:

```python

           "msg": "审查跳过(模型不可用),直接进入真实运行"})

`【面试】` 为什么 fail-open?**审查是增强项,`verify` 才是确定性兜底**。审查挂了就不出结果,等于把增强项变成了单点故障;而放行之后还有真跑这一关,风险可控。

### 6.6 连续打回的工程兜底

`backend/graph.py:262-273`:

```python

### 6.7 验证:永远由代码判定

`backend/graph.py:299-304`:

```python

### 6.8 轮次语义与 gate 字段

`attempts` 里每条都带 `gate`:

| gate | 含义 | 前端显示 |
|---|---|---|
| `critic` | 审查打回,没跑过 | "审查打回" |

### 7.2 L1:精确查表

`backend/kb.py:66-85`:

```python
def _l1_search(etype: str | None, message: str) -> list:
    load_entries()
    if not etype:
        return []
    same = _by_type.get(etype) or []
    specific, generic = [], []
    for e in same:
        pats = e.get("message_patterns") or []
        if not pats:
            generic.append(e)
        elif any(re.search(p, message, re.IGNORECASE) for p in pats):
            specific.append(e)
    return specific or generic
```

三条规则:

1. **类型必须完全一致** —— `_by_type` 是倒排表
2. **同类型内按消息正则细分** —— 例如 5 条 SyntaxError 靠 `expected ':'`、`was never closed`、`invalid character` 区分
3. **具体优先,兜底其次** —— 正则都没命中,才用该类型下 `message_patterns` 为空的兜底条目

`【核心】` 异常类型是解释器给出的**硬标签**,不是自然语言。用它做 key,准确率是 100%;用语义相似度去猜,一定会有误差。

### 7.3 L2:向量兜底

`backend/kb.py:217-234`:

```python
def _l2_search(query: str, k: int) -> list:
    load_entries()
    store = _get_vectorstore()
    if store is None or not query.strip():
        return []
    results = store.similarity_search_with_score(query, k=k)
    hits = []
    for doc, distance in results:
        if distance > config.KB_MAX_DISTANCE:   # 默认 0.45
            continue
        eid = (doc.metadata or {}).get("entry_id") or doc.id
        e = _by_id.get(eid)
        if e:
            hits.append(e)
    return hits
```

索引重建判断(`kb.py:167-206`)用**双指纹**:

```python
current = f"{_corpus_hash()}|{fp}"     # 语料哈希 + 嵌入后端标识
if stored != current or count == 0:
    store.reset_collection()
    store.add_texts(...)
    _HASH_FILE.write_text(current)
```

`【核心】` 只用语料哈希不够。换了 embedding 后端(ollama ↔ siliconflow),向量空间变了,旧向量必须全部重建,否则检索质量会莫名其妙下降。

### 7.4 为什么 L1 优先:实测数据

同一批 18 条真实报错(18 类各一条):

| 模式 | top1 正确 | top3 含正确 | 无召回 | 平均耗时 |
|---|---|---|---|---|
| L1 | 18/18 | 18/18 | 0 | ~0.1 ms |
| 向量 @0.45 | 11/18 | 13/18 | 3 | 253 ms |
| 向量 @0.55 | 13/18 | 17/18 | 0 | 215 ms |

`【核心】` 向量的错误不是"没命中",而是"命中错的":`IndexError` → `valueerror-not-in`、`KeyError` → `nameerror-undefined`、`expected an indented block` → `indentation-unexpected`(方向相反)。对初学者,给错方向的建议比不给更糟。

### 7.5 三种检索模式

`backend/config.py:36-41`:

```python
KB_MODE = os.getenv("CD_KB_MODE", "auto").strip().lower()
```

| 模式 | 行为 |
|---|---|
| `auto`(默认) | L1 优先,未命中走 L2 |
| `vector` | 跳过 L1,每次都走向量;向量不可用时不回退(严格模式) |
| `l1` | 只用 L1,不走向量 |

`【易错】` 切成 `vector` 时,阈值要从 `0.45` 放宽到 `0.55`,否则 18 条里有 3 条直接无召回。生产默认保持 `auto`。

### 7.6 一个同源的隐式依赖 bug

`_l1_search` 和 `_l2_search` 都依赖 `load_entries()` 先建索引。原代码只有 `kb.search()` 会先调用它,所以直接调用 `_l1_search` 时 `_by_type` 是空字典,**永远返回空**。

`【核心】` 修复方式不是"在调用方记得加一行",而是**让函数自己保证前提**:

```python
def _l1_search(...):
    load_entries()   # 幂等缓存,重复调用零成本
```

`_l2_search` 后来也踩了同一个坑(分诊直接调用时 `_by_id` 为空,向量命中被全部丢弃),同样在函数内补了加载。

`【面试】` 这是很好的"防御性编程"案例:**不要依赖调用顺序,要让函数自己满足自己的前置条件**。

### 8.2 为什么需要"代码块保护"

    """切分前把代码块替换为占位符,防止:
    ① 代码块被劈开
    ② 注释里的 # 被当标题切

    blocks = []

## 9. 流式诊断:SSE + 增量 JSON 状态机

### 9.1 为什么不能直接吐 JSON

模型输出的是:

```json
{"explain":"程序在计算平均值时...","reason":"...","fix_points":[...],"fixed_code":"..."}
```

直接把这个流给用户看,用户看到的是 `{"explain":"程`——又丑又没意义。需要一层**边生成边抽取**。

### 9.2 事件协议

| 事件 | 字段 | 前端行为 |
|---|---|---|
| `status` | stage / round / msg | 更新状态行("正在检索…") |
| `field` | field / phase=start | 新建字段容器 / 结束 |
| `delta` | field / text | 追加文字(打字机) |
| `item` | field=fix_points / text | 追加一条修改点 |
| `result` | data | 切换完成态卡片 |
| `error` | message | 显示错误 |
| `done` | —— | 关闭流 |

### 9.3 状态机:逐字符处理

`backend/stream_json.py:132-247`,核心状态:

```text
seek → key_open → key_str → colon → value
                                      ├─ 目标字符串 → str(实时抽 delta)
                                      ├─ 目标数组   → arr → arr_item(逐条抽 item)
                                      └─ 其他       → skip_* (跳过,不解析)
```

关键设计:

- **任意切分安全**:按字符处理,不假设 token 边界
- **永不抛异常**:任何看不懂的输入都静默停发,最终由完整 JSON 解析兜底
- **顺序无关**:字段按模型实际生成顺序处理,先到先发

`backend/stream_json.py:44-66` 的 `_StrSink` 还要处理转义与 `\uXXXX`:

```python
if ch == "\\":
    self.mode = 1          # 进入转义
    return False
if ch == '"':
    return True            # 字符串结束
self.put(ch)
```

### 9.4 后端:线程 + 队列

`backend/main.py:112-139`:

```python
def gen():
    events = queue.Queue()

    def worker():
        try:
            result = graph.run_diagnosis_stream(..., sink=events.put)
            events.put({"type": "result", "data": result})
        except Exception as exc:
            events.put({"type": "error", "message": ...})
        finally:
            events.put(None)          # 结束哨兵

    threading.Thread(target=worker, daemon=True).start()
    while True:
        event = events.get()
        if event is None:
            break
        yield _sse(event)
    yield _sse({"type": "done"})
```

`【核心】` 为什么不用 `async`?因为 LangGraph 的 `invoke`、`subprocess.run`、OpenAI SDK 的同步调用都是阻塞的。用"后台线程跑同步逻辑 + 队列桥接"最简单,也不会阻塞事件循环。

`【易错】` 一定要有结束哨兵 `None`。否则生成器永远等 `queue.get()`,SSE 连接不关闭,前端一直转圈。

### 10.2 意图识别:两种意图

判断要点:

> 消息是否指向一个**目前还没有实现、值得实际试一下**的具体改法?
> 是 → alternative;只是问已经发生的事为什么行/不行 → question。

`【易错】` 这是项目里真实修过的边界。"为什么把 X 改成 Y 之后就不报错了"是**问原理**,不是提替代方案;第一版分类器把它误判成 alternative,白白重跑了一遍。

LLM 失败时退化为关键词兜底(`chat.py:248-253`):

```python
_ALT_HINTS = ("为什么不那样", "为什么不直接", "为什么不用", "为什么没有用", "换成", "改成",
              "改用", "试试用", "试试改", "能不能用", "应该用")
```

### 10.3 替代方案闭环

`backend/chat.py:342-455`,流程:

```text
生成代码(严格按用户思路)
  → 真实运行
     → 通过:自然总结 + 更新 chosen_fix + 记录 alternatives
     → 没通过:带真实报错重试(≤ CD_CHAT_ALT_ROUNDS,默认 2)
        → 仍失败:生成结构化解释
```

`【核心】` 用户点名的库/机制**不能被替换**。真实案例:用户问"能不能用 scipy 算平均",环境没装 scipy,第一版重试时模型偷偷换成了 numpy,假装跑通。修复(`chat.py:303-306`):

```python
parts += ["", "【历次尝试(都没跑通,请修正实现细节;用户思路保持不变)】",
          "注意:不得把用户指定的库或机制替换成其他东西;若真实报错表明用户指定的机制"
          "在当前环境或语言中不可用,请把 feasible 设为 false,并在 reason 里引用真实报错。"]
```

再加确定性检测(`chat.py:404-412`):真实报错是 `ModuleNotFoundError` 且缺的正是用户点名的库 → 直接判"不可执行",不再重试。

`【面试】` 这是"忠实于用户意图"的典型设计:模型可以优化实现细节,但不能偷换目标。

### 10.4 结构化失败解释

`chat.py:477-481` 要求模型输出五段:

```json
{
  "summary": "一两句口语化总结",
  "reasons": ["具体原因,引用真实报错"],
  "limits": ["技术限制(语言机制/环境/依赖)"],
  "issues": ["强行按这个方向改会带来的潜在问题"],
  "suggestion": "接下来怎么办"
}
```

失败时还有规则兜底 `_rule_explain`(`chat.py:518-531`):只拿真实运行证据说话,不编造。

### 10.5 上下文怎么组装

`_context_block`(`chat.py:100-160`)按固定顺序拼:

1. 原始代码 / stdout / stderr / 报错定位
2. 已有诊断结果(explain / reason / fix_points / 修复代码 / 验证输出)
3. 跑通场景的"上一轮诊断"(旧代码 / 旧报错 / 旧诊断)
4. 当前采纳的修复(如果替代方案通过过)
5. 已尝试过的替代方案(避免重复建议)

`【核心】` 传的是**结构化事实**,不是"对话摘要"。多轮系统最常见的死法就是"把上下文压缩成一句话",细节全丢。

## 11. 前端:Monaco 标红与渐进渲染

### 11.1 一行标红

`frontend/src/components/MonacoEditor.vue:69-80`:

```javascript
function markErrorLine(line) {
  const target = Math.min(Math.max(Number(line), 1), model.getLineCount())
  const range = new monaco.Range(target, 1, target, model.getLineMaxColumn(target))
  const options = {
    isWholeLine: true,
    className: 'cd-error-line',
    glyphMarginClassName: 'cd-error-glyph',
    inlineClassName: 'cd-error-squiggly',
    overviewRuler: { color: '#e24b4a', position: monaco.editor.OverviewRulerLane.Right },
  }

```

`【易错】` 行号要先 clamp 到 `[1, lineCount]`。模型返回的 `error_line` 可能越界(比如用户代码已经被改短了),不 clamp 会抛异常。

### 11.2 一键填回,保留撤销栈

`MonacoEditor.vue:57-66`:

```javascript
editor.executeEdits('codedoctor-fix', [
  { range: model.getFullModelRange(), text: code },
])
editor.pushUndoStop()
editor.setPosition({ lineNumber: 1, column: 1 })
```

`【核心】` 用 `executeEdits` 而不是 `setValue`。`setValue` 会清空撤销栈,用户按 Ctrl+Z 回不去;`executeEdits` 是一次可撤销的编辑操作。

### 11.3 流式渲染状态

`App.vue` 里维护一个 `stream` 对象:

```javascript
{
  stage, msg, round,                 // 状态行
  explain, reason, fix_points,       // 逐字/逐条填充
  fixed_code,                        // 逐行流出
  ...                                // 完成前的临时态
}
```

收到 `field/delta/item` 就改对应字段,Vue 自动重渲染;收到 `result` 就把 `stream` 置空、切到 `diag` 完整卡片。

`【核心】` 流式和完成态是**两套 UI**:流式卡只负责"让用户看到进展",完成卡负责"结构化展示 + 操作按钮"。不要在流式卡上做复杂交互,否则状态很容易乱。

## 12. 安全边界:这不是沙箱

### 12.1 隔离了什么

| 维度 | 现状 |
|---|---|
| 工作目录 | 独立临时目录,结束清理 |
| 标准输入 | 关闭 |
| 运行时长 | 10 秒超时 |
| 输出体积 | 读完后截断 2 万字符 |

### 12.2 没隔离什么

| 维度 | 风险 |
|---|---|
| 文件系统 | 绝对路径可读写任意文件 |
| 环境变量 | 完整继承,包括 `CD_API_KEY` |
| 网络 | 不受限,可访问外网与本机服务 |
| 子进程 | 可 `Popen`,超时只杀直接子进程 |
| 内存/CPU | 无限制 |
| 权限 | 与后端同权限 |

### 12.3 三个具体风险

1. `print(os.environ["CD_API_KEY"])` 可以把密钥打到 stdout,原样返回前端
2. `subprocess.Popen(...)` 派生的进程在超时后仍然存活
3. CORS 是 `allow_origins=["*"]`(`main.py:28`),浏览器里任意网页都可能向 `127.0.0.1:8000/api/run` 发请求

### 12.4 结论与加固

`【核心】` **本地单用户自用可以接受,对外提供服务绝对不行。** 加固顺序:

1. CORS 收紧到前端地址
2. 环境变量改白名单,不传 `CD_*`
3. 超时后用 `taskkill /T /F` 杀进程树
4. Job Object 限制内存/进程数
5. 真要对外:Docker(`--network none --read-only --memory 256m --pids-limit 64`),或 gVisor / Firecracker

`【面试】` 准确说法:**"执行引擎是子进程级隔离,不是安全沙箱;产品定位是本地单用户工具,信任边界是使用者本人。"** 不要含糊说"做了沙箱"。

## 14. 高频面试问答

### Q1:这个项目是 Agent 还是 Workflow?

**Workflow。** 严格按业界分类:模型只负责"内容"(诊断文字、意图标签、替代方案代码),不负责"流程";下一步做什么由 `graph.py` 的边决定,不由模型决定。

`【面试】` 加一句:"诊断顺序是物理确定的——不跑代码就不知道报错,不验证就不能说修好。让模型决定要不要验证,等于把最确定的环节交给最不确定的东西。"

### Q2:那三个角色算多智能体吗?

广义算"多角色协作",严格不算"多智能体系统"。区别在调度权:

| | 你的项目 | 自主多 Agent |
|---|---|---|
| 下一步 | 代码决定 | 模型决定 |
| 工具选择 | 节点内固定函数 | 模型自主选 |
| 循环次数 | 常量 3 | 模型判断 |

`【面试】` "三个角色各有独立 prompt、独立 schema、独立上下文,通过结构化 State 通信;编排是固定的,因为诊断流程本身是确定的。"

### Q3:Agent 之间用什么协议通信?

**没有协议,共享 State。** 三个角色在同一个 Python 进程、同一张图里,节点之间是函数调用,State 是 TypedDict,后写覆盖。没有序列化、没有网络、没有握手。

`【面试】` "协议解决的是进程边界问题。同进程引入协议,只会多出序列化和故障点。真要跨机部署,再把节点包成 HTTP 服务;要对其他厂商开放,才需要 A2A。"

### Q4:为什么知识库先查 L1?

异常类型是解释器给的硬标签,不是自然语言。实测同一批 18 条报错:L1 top-1 18/18,向量 top-1 只有 13/18,而且错配方向危险(IndexError→ValueError、KeyError→NameError、该缩进→多缩进)。

`【面试】` "L1 用 20 行代码把候选从 30 条缩到 1 条,省掉一次 embedding 调用和一堆语义噪声;向量只负责兜没收录的长尾。"

### Q5:为什么验证必须由代码完成?

`【面试】` "一旦让模型判断'这个修复应该可以了',项目就从医生退化成算命。`runner` 真跑 + traceback 解析是确定性的,这是产品的立足点。"

### Q6:审查为什么 fail-open?

"审查是增强项,`verify` 才是确定性兜底。审查挂了就不出结果,等于把增强项变成单点故障;放行之后还有真跑这一关。"

### Q7:为什么流式要自己写 JSON 解析器?

"模型输出是结构化 JSON,直接把原始 token 吐给用户,看到的是 `{\"explain\":\"程`。需要一个逐字符状态机,在 JSON 还没闭合时就把目标字段抽出来。要处理转义、`\uXXXX`、代理对、任意分片边界,所以不能简单用 `json.loads`。"

### Q8:多轮追问怎么保证上下文不丢?

"服务端会话保存代码、真实报错、诊断结果、全部消息;传给模型的是结构化事实(原始 stderr、每轮尝试记录),不是对话摘要。后端重启时,前端把历史消息带上来恢复对话链。"

### Q9:这个项目最大的技术难点是什么?

可以答三个层次:

1. **流式增量解析**:JSON 未闭合时抽字段,任意切分安全
2. **多角色上下文隔离**:三套 prompt/schema/参数,靠 State 传结构化结果
3. **降级链**:结构化 → JSON → 规则;流式 → 非流式;每层都要保证最终有可用结果

### Q10:如果让你重做,会改什么?

- 执行引擎换容器/Job Object,把"能跑"升级成"安全地跑"
- 审查角色在 DeepSeek 上重测,7B 的误杀率不足以评价架构
- 知识库语料从 30 条扩到 100+,并按真实用户报错分布补充正则
- 加一个"修复前后行为对比"的测试:不仅看跑没跑通,还看输出是否等价

### 参考答案

1. `exec` 跑在服务进程里,无法超时终止、崩溃会污染服务、traceback 行号是 `<string>`;子进程可杀、隔离、报错真实。
2. 不能。`cwd` 只影响相对路径;绝对路径仍可读写,这是进程级隔离不是权限隔离。
3. `specific` 是 `message_patterns` 正则命中的条目;`generic` 是该类型下没有正则的兜底条目。具体优先,都没命中才用兜底。
4. 语料变了要重建;嵌入后端变了向量空间也变了,旧向量不能混用。
5. 区分"审查打回"和"验证未通过"。没有它,前端会把没跑过的一轮显示成"运行报错"。
6. `llm.review()` 返回 `None` 时,节点直接返回 `verdict=pass, skipped=True`,继续真跑。
7. 因为输入可能任意截断/畸形;解析失败就停发事件,最终由完整 JSON 解析兜底,不能因为流式中途出错让整个诊断失败。
8. 否则 `queue.get()` 永远阻塞,生成器不结束,SSE 连接不关闭,前端一直转圈。
9. 真实报错是 `ModuleNotFoundError` / `ImportError`,且缺失的模块正是用户在方案里点名的库。
10. `setValue` 清空撤销栈;`executeEdits` 是一次可撤销编辑,用户能 Ctrl+Z 退回。
11. 三种:已验证通过;没有修复代码(规则模式);轮数用尽仍未通过。
12. 代码块会被 Markdown 标题切分器劈开,注释里的 `#` 会被误判成标题,召回半截代码。
13. 已经打回过一次,说明审查自己也不确定;真跑是确定性的,误杀代价高于漏审。结果标 `overridden`,前端提示"审查仍有疑虑"。
14. `_by_id` 为空,向量命中的 doc 无法还原成条目,全部被丢弃,函数永远返回空。
15. 在 `verify` 里同时运行原代码与修复代码,比较 stdout(或关键变量);原代码本来就报错的场景,比较"正常输入分支"的输出。注意异常输入要排除。
16. 网络隔离、只读文件系统 + 唯一可写临时目录、内存/CPU/进程数限制、非 root 低权限用户、系统调用过滤(seccomp)或微虚拟机。
